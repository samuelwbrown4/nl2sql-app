# SchemaSpeak

Ask your systems questions in plain English!

 SQL answers pulled live from a production database, and instructional query results pulled from your own documentation through one shared architecture.

**Live demo:** https://schema-speak.com

---

## What it does

SchemaSpeak has two modes, both driven by the same underlying idea of giving an LLM a scoped information on what is available, let it reason over the query with the provided context/scope, then let the backend execute the LLM's result against the real data.

**SQL Mode** — ask a plain English question about a live database ex: "how many shipments are currently in transit?" and get back a synthesized, plain english answer, not just a raw result set. These informational queries can be supported by multiple data sources through a dropdown.

**Document Mode** — ask "how do I create a shipment?" and SchemaSpeak searches an index of QRGs/SOPs by tag and description, pulls the best-matching document, and returns a synthesized answer grounded in that document's actual content. Documents can also be written directly in the app by describing a process in natural language and getting back a generated QRG to review and publish. Documents cas also be uploaded (`.md`, `.txt`, `.docx` all supported) and indexed automatically with metadata generated by the LLM to be used for future "how to" queries.

Signed-in users can favorite queries in either mode for quick access /reusability, and browse/search/filter the full document library, with view and direct download for any file.

## Why

Most companies have people constantly asking for one-off reports. Think "busy upper-management" who only want the answer to a simple question but have to pore through a report to get there. Conversely, many lower level employees may not have access to certain reports, or dont know how to interpret them. SchemaSpeak solves this by allowing users to get their answer quickly and easily, without distracting from important operations.

 Another example of operational and organizational inefficiencies stem from having to ask a coworker or an admin "how do I do X" because the answer lives in a doc nobody can find. By allowing users to ask a simple question, they can become self serving, saving them, and their coworkers time from having to dig through folders to find the appropriate material.

## Architecture

```
React (Vite) frontend  →  Express backend  →  Anthropic API (Claude Haiku)
       ↓                        ↓
   AWS Amplify            ┌─────┴─────┐
                     Source database   S3 (doc storage + config)
                    (read-only role,   Supabase (users, favorites)
                     peered VPC)
```

- **Frontend:** React + Vite + Mantine, deployed on AWS Amplify, custom domain via Route 53
- **Backend:** Express on EC2, reverse-proxied through Nginx with a Let's Encrypt cert for HTTPS
- **LLM:** Anthropic API (Claude Haiku) — separate prompts for SQL generation, multi-step query planning, result synthesis, document routing, document-answer synthesis, and QRG/metadata generation
- **Source data:** Live connection to a production PostgreSQL database (a TMS system) over a peered VPC, through a dedicated read-only database role scoped to specific tables
- **Document storage:** S3 — original files stored as-is (no format conversion), fetched and parsed on demand at read time; a JSON config in the same bucket indexes every document by tags, system, and description
- **App data:** Supabase (Postgres) for users and favorited queries, JWT-based auth (bearer token, not cookies)

## Key design decisions

**Schema is config, not introspected live.** Each source has a hand-curated JSON config listing exactly which tables and columns are queryable, plus plain language notes for relationships that don't reduce to a simple foreign key (e.g., a column whose join target depends on another column's value) and frequent errors notes to help the LLM know what operations it has tripped up on in the past. These notes would be updated and maintained as errors are discovered and determined to be an LLM interpretive mistake rather than a malformed query. Sensitive tables and columns are simply never written into the config and never even in the LLM's context at all. A dedicated read-only database role enforces the same boundary at the database level.

**Documents keep their original format.** Uploaded `.docx` files are stored as their original bytes, not converted to markdown on ingestion. Text is extracted on demand, at read time, whenever it's needed (for LLM prompts, for in-app document viewing, etc.) rather than storing a separate derived copy. This was a deliberate choice over a "convert once at upload" approach since converting to markdown would potentially end in loss of content (specifically, it discards embedded images), and a document has exactly one authoritative version, not two representations that can drift out of sync.

**At least two-step LLM pipelines, everywhere.** SQL generation and result synthesis are separate calls, so results are shown in plain English, not raw rows. Document routing and document-answer synthesis are separate calls, so the routing decision only ever sees lightweight metadata (titles, tags, descriptions), never the full document text which allows for keeping that prompt small regardless of library size. 


## Tech stack

- React, Vite, Mantine, react-markdown
- Node.js, Express, multer, mammoth (`.docx` text extraction)
- PostgreSQL (source data + Supabase for app data)
- Anthropic API (Claude Haiku)
- AWS: EC2, S3, VPC (with peering), IAM, Route 53, Amplify
- Nginx, Let's Encrypt (certbot)
- JWT authentication, bcrypt

## Local setup

```bash
# Backend
cd server
npm install
# populate .env — see .env.example
node index.js

# Frontend
cd client
npm install
# populate .env — see .env.example
npm run dev
```

Required environment variables (backend): `ANTHROPIC_API_KEY`, source database credentials, `APP_DB_URL` (Supabase), `JWT_SECRET`. S3 access uses an IAM role attached to the EC2 instance in production; for local development, AWS credentials need to be available through another provider (e.g. a local AWS CLI profile).

Required environment variables (frontend): `VITE_API_URL`.
